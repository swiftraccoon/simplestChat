# Signed musl native staging in disposable Debian

The manual **Signed musl release stage KVM runtime** workflow is a deliberately
bounded fixture for the installed `simplestchat-ops release stage` operation.
It requires a successful current-main CI run/attempt and that attempt's **signed
Ops** artifact. The separately selected **signed server** contract must match the
same revision, run and attempt. Unsigned producer artifacts do not qualify.

The controller compiles trusted GNU Ops and xtask before the sole API credential
leaf. It retains the original tools, trusted source files and payload namespaces.
The Ops contract has fifteen files and three signed subjects. Acquisition performs
three real verifications; a second actual retained verification performs three
more after all originals have been held. Only then does the existing thirty-three
case Ops guest suite install the authenticated musl binary. The first install
must report changed; exact repeat must report unchanged. A saved success JSON or
newly self-derived binary hash does not confer installation authority.

The eleven-file server contract has four signed subjects. Its initial signed
acquisition performs four real verifications. Before transferring any server
payload, the keeper retains all eleven original files and their directory/member
namespace, performs two checked private GitHub metadata API reads, and compares
repository, successful main-push CI, exact revision/run/attempt and artifact ZIP
size/digest against those held originals. It then invokes the actual existing
`release attestation verify --directory … --selection-json …` command for four
more signature verifications. That cached command verifies bytes and signatures;
it does not itself establish current API identity. There are six Ops and eight
server signature verifications, plus the two explicit current server API reads.
All current authentication roles use the original checked private GH tool path.

Only `release.json` and `image.tar` are copied to the canonical guest release
directory. Their root ownership, private modes, bytes and digests are checked
against the authenticated controller originals before the candidate executes.
All eleven controller originals remain held through finalization. Before/after
namespace witnesses detect persistent changes; they do not eliminate every
transient same-UID substitution and restoration race.

The guest is the existing pinned Debian13 cloud image under real free-runner KVM,
with generated enrolled SSH keys, a root-only run marker and loopback-only SSH
forwarding. Its new fixture playbook imports the unchanged signed/pinned Docker
provisioning task closure. It does not run host sysctl/build provisioning, public
application deployment, database migrations, backup, restore or rollback. Cold
APT/Docker setup is measured as fixture overhead. No production Python helper,
installed caller, installer upgrade rule or bootstrap route changes.

The same authenticated installed musl inode is retained and executed by FD for
first staging and exact repeat. Required native budgets remain explicit:
`0 < M < N <= 600`. The fixture uses M60 and clips N to remaining work in its one
original clock. Its stricter admission requires N at least130 (including the
native40-second validator tail inside body, local settlement and useful work)
and at least300 seconds before the two-call guest handoff. It refuses admission
when those fixture allowances no longer fit; these are not new product defaults.
The original fixture lasts1800 seconds, with body1680 and finalization120; auth,
cloud-image/boot, cold Docker setup, both native calls, observation and cleanup
share it. Retries and trials never reset it. Blocking OS I/O/close/reap does not
have a hard-wall guarantee. Slow otherwise valid inputs can be refused.

First staging must load the actual image, validate its packaged SHA384 migration
map, persist a finalized journal/staged record and leave no known validator.
The independent observer checks the actual daemon image's profile and ordered
RootFS against the authenticated archive graph. Docker may identify that image
by its verified config digest or by the exact selected verified OCI image-manifest
digest. An unrelated index/blob digest or a syntactically valid foreign image is
not accepted. Full Docker configuration/environment values remain private.

Historical Docker events are queried over completed bounded windows beginning
before the first call. The original native attempt's validator name/ID and fixed
immutable image must match a complete create/start/die0/destroy actor sequence.
The repeat window begins at the same original timestamp and must still contain
that full first sequence, with no second native validator. Its retention is a
history-eviction anchor; finite source command counts and fewer than256 events
are required. Missing/truncated/overflow or uncertain histories fail the proof.
Exact repeat must retain the same staged inode, bytes and staged timestamp and
produce only the source-bound image-inspect command evidence. It must not load
or validate again. Protected configuration/helper/installed inputs and daemon
container/network/volume sets remain unchanged except expected staged images.

After the native windows, the observer creates a separate uniquely labelled
checksum probe using the immutable selected image. It independently inspects
that exact container's user, readonly root, no network/mounts, dropped caps,
no-new-privileges and finite CPU/memory/PID/log settings before execution. Its
fixed timeout/checksum command must exit0 and produce the exact signed migration
map; the exact owned container is removed and absence checked.
**This separately inspected probe proves its own isolation profile. It does not
independently observe the native validator's transient HostConfig.** The summary
keeps native actor-lifecycle evidence and separate-probe isolation facts distinct.
No missed transient inspection is counted as successful native isolation proof.

Direct guest child completion proves leader status and pipe EOF; it does not
claim whole-group retirement after consuming reap. Remaining guest descendants
are retired by the exact final VM owner. Consumed child groups are never signalled.

All known peer finalizers are attempted after the first failure. Cleanup addresses
only exact retained owned container IDs and the exact VM process; there is no
broad image/container prune or foreign-resource cleanup. The keeper retains fixed
bounded private prefixes of guest observer/native command evidence before VM
retirement, explicitly marking truncation. These raw diagnostics are never
uploaded and cannot establish authentication or success. Only the closed sanitized
summary is uploaded after workflow success. Actual QEMU0, SSH/cloud-init/QMP EOF,
drainer completion, input/namespace/lock checks, private-work retirement and final
stdout/handler/umask/signal/clock fences are mandatory.

This unit's authoring and inert checks do not establish actual authenticated
musl execution, KVM, Docker load or native staging. Those claims require the
same-head signed contracts and a successful real manual workflow. Even a passing
fixture does not prove application readiness, live-service interruption behavior,
database migration execution, production traffic, upgrade, rollback or caller
cutover. Its scope is complete native staging with the stated observation limits.
