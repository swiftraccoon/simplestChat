# Signed musl host deployment fixture

This manual free GitHub KVM fixture is designed to exercise a complete installed-musl
host deployment and one deliberately failed replacement with successful rollback.
The complete 97-case native/unchanged-Python comparison passed locally in 365.12
test seconds (367.785 seconds wall). Those fixtures use real private files, locks
and owned inert children, with inert Docker/database/readiness replies. The VM
controller/guest previously passed 32 inert tests, and the corrected ordinary Ops
suite passed 484 tests. The earlier barrier had 55 passing local inert tests,
including actual private files, local socketpairs and checked first-cause faults.
Actual run `40146220125` at `e271a8c` completed and validated
the signed-musl positive transaction, including its real Docker, PostgreSQL,
Caddy/TLS, backup, actor and continuity checks. It then failed at `negative-report`:
the intended failed replacement instead returned native exit zero, `passed: true`
and phase `complete`. The controller retained one completed trial and successful
VM/input cleanup with QEMU zero. This is a failed whole fixture; rollback remains
unproved. The revised negative coordination described below has not run in a VM.
Production Python, installed callers, bootstrap and upgrade policy remain unchanged.

Select a successful same-head main CI run and its signed Ops and server B
artifacts. Separately select an explicit old successful main CI run, attempt,
revision and signed server A artifact with exactly the same packaged schema.
The `Signed musl host deploy KVM runtime` workflow accepts only those fixed
selectors. It compiles the trusted GNU client and artifact controller before
the credential-bearing leaf. Actual execution requires a disposable GitHub
Linux runner with KVM; it never targets a real VPS or production traffic.

Current checkout identity is never evidence of old A. Each server retains
eleven original files and its namespace, fresh-revalidates two exact API
metadata roles, then performs four retained signature-verifier roles. Initial
and retained verification total eight signature calls per server. Ops uses its
three subjects before and after retaining the originals, six signature calls,
and the existing actual first/repeat installation and 33 ordered cases. Counts
in the report represent completed successful roles, not a replacement for
original custody. All GH roles use the checked private tool environment.

Only A is loaded during fixture bootstrap. Authenticated B's canonical archive
and manifest are transferred, and actual installed-musl `release deploy` must
perform its own staging/import. The positive transaction replaces A with B.
A second transaction targets A. Its Docker dependency uses the fixed
`negative-inspection-response-barrier-v1` fixture profile. Only this native call
runs in a private mount namespace; the positive call uses `original-docker-cli`.
The original parent Docker inode and authenticated installed Ops binary stay
unchanged. The namespace binds an original-CLI alias and a source-pinned fixed
interposer before native tool discovery. Every nonmatching argument vector execs
the original CLI. Only the exact native application-inspection format and full
container ID can enter a private, bounded local socket exchange.

The parent joins that request to the new private `replace_application` attempt,
current selected app, exact fixture labels and authenticated A image. It captures
the real successful running inspection, stops that exact known ID and observes it
stopped, then fsyncs and checked-closes a private receipt and its directory. Only afterward can the
wrapper forward the original inspection bytes and status. It never fabricates a
running or readiness reply. The fixed client has no subprocess; actual Docker
queries and the stop remain owned by the existing parent command owner. The
mount-entry children inherit the owned group. Parent service has a narrower
20-second cap from its actual entry, clipped to the same original body. Native's
unchanged 30-second inspection deadline remains authoritative; the fixture does
not reconstruct its exact start or claim hard cancellation of blocked I/O.

The native caller must then exit nonzero at the readiness deadline in replacement,
report attempted successful rollback, restore B and finalize the rollback journal.
The actual stop receipt, full daemon history and all independent continuity checks
remain mandatory. This is an explicitly interposed negative dependency profile,
not proof that the negative used byte-identical original CLI dispatch. Unknown
identity, bad frames, vanished peers, late work or receipt/reply/close failure
refuse the fixture. A missing stop, unrelated earlier refusal, recovered stop or
passive JSON claim cannot substitute for rollback. No derived images or Python
deploy fallback establish either result.

The guest runs real PostgreSQL and Caddy with a guest-local generated CA and
trusted TLS. Independent observations bind the signed image graph, selection,
assets, exact successful schema, fixed seed aggregate and marker, unchanged
PostgreSQL/Caddy IDs, starts, restarts and configuration hashes. Both actual
custom dumps, list results and receipts are checked against retained originals.
A listed dump is not a restore rehearsal. Docker identity may be the signed
config ID or the selected verified OCI image-manifest ID; an arbitrary index
or unrelated otherwise-valid image is insufficient.

Native actor proof uses complete bounded historical Docker events, the actual
numbered create stdout IDs and retained final name journals. It does not guess
command positions: a fresh transaction creates two validators and two browser
capture actors. Validators must create, start, exit zero and disappear; browser
capture actors must never start. Missing anchors, incomplete histories or 256
or more events refuse. Native ledger, dump and list exec events admit only the
exact retained PostgreSQL container, fixture label and known image identity;
dependency lifecycle changes remain forbidden. A separate unchanged Stage
checksum probe is inspected
and retired independently. Its isolation proves only that probe's profile;
actual native validator isolation is explicitly not independently inspected.

One fixture entry clock is 4,500 seconds with 180 seconds for finalization.
Its body is 4,320 seconds: two full native 1,800-second envelopes plus 120 seconds
for independent observations and SSH settlement leave a strict 600-second setup
admission. Cold Docker/database/proxy setup is unmeasured and may refuse a valid
trial. The earlier successful Stage run `40128571380` at `a8653a7` measured
107.173 seconds for cold Docker setup alone. That excludes this new fixture
database/proxy setup and both deployment calls, and does not establish that
complete setup fits 600 seconds. Native M60, rollback reserve 576 inside B,
and production caller limits
remain unchanged. A persistent fixed prepare/continue guest session retains the
same control and original FDs. Only remaining durations cross the host/guest
boundary; their monotonic epochs are never compared. No phase restarts a clock.

Only a closed bounded nonsecret completed summary is uploaded. Original
payloads, configuration, dumps, credentials, raw streams, SSH keys and signed
URLs remain private. Private failure retention selects only fixed bounded
observer/native output prefixes and outcome/name diagnostics. It excludes dump
bytes, environment files, curl configurations and certificate private keys.
Known full owned container IDs and the generated CA are settled before guest
success. No broad image/container prune occurs. The outer fixture also requires
all SSH/QMP/VM/stream/known-host/source owners, actual QEMU zero, restoration and
the original final clock fence. Earlier frames remain passive through final
status. Before/after original witnesses do not eliminate every same-UID
swap-and-restore race.


## Bounded failure diagnostics

A failed runtime trial stays failed. The controller retains only a closed
metadata projection in `summary.json`; the workflow uploads that fixed file
after success or failure when it exists. No raw guest/native stream, environment,
configuration, credential, certificate key or database dump is uploaded. Missing
evidence never authorizes a positive result. The workflow conclusion and final
controller exit status remain authoritative: a late output/restore/fence failure
can invalidate earlier JSON bytes.

The guest snapshots its semantic checkpoint and last admitted fixed observer
role/ordinal/status before fixture cleanup can overwrite them. These identify
what was observed at the failure boundary; they do not assert that the last
command caused the failure or that a daemon-side operation was undone. The
checkpoint distinguishes positive/negative native execution, report parsing,
saved outcome/journal/staged/backup validation, actor history and continuity.
The completed-trial count is separate from a native child exit.

A native raw signed leader exit is retained separately from selected passive
`passed`/`phase` JSON fields. The report may claim success while the child exits
nonzero; neither field alone authorizes the runtime proof. Fixed reviewed
native/policy/asset failure literals map to closed labels. A numbered native
command refusal can expose its bounded ordinal. Unknown text is only
`other-refusal`; arbitrary unknown keys, URLs, paths, values and exception
messages are never copied into the public projection. Malformed diagnostics
are unavailable, not a replacement for the original failure.

The marker-bound `--failure-diagnostic` guest route reads only its fixed private
diagnostic record through existing bounded nofollow owners. It selects no
command, stream or arbitrary path. The controller collects it only after a
failed body, under the same original final end, and still attempts all known
peer finalizers. These facts are passive diagnostics, not authentication or a
saved-success capability. The snapshot precedes guest finalizers; it does not
claim to observe every later guest teardown error.

Original live body/setup fences run before widening to cleanup/exercise, even
when an earlier failure is already latched. Cleanup never resets the entry
clock or clears the primary failure. The fixture budgets4500/600/180 and native
1800/60 remain unchanged. Local synthetic checks exercise hostile diagnostic
JSON, first-anchor preservation across cleanup, actual owned child raw-exit
capture, prior-trial reset, exact body/setup boundaries and all known closes.
They do not establish a successful authenticated VM deployment.

The first real signed host-deploy trial failed after authentication and initial
fixture readiness; its VM and original-input cleanup completed. Its prior
success-only artifact rule lost the private failure context. The later bounded
diagnostics established the successful positive and missed negative described
above. A source-derived inert counterexample executes the prior observer and
health callback across its one-second blind interval: native inspection,
readiness and completion can all finish before another poll is admitted. This
does not recover the failed runner's exact timing. The deterministic barrier
repairs fixture ordering; no native/core behavior, DB policy, caller or budget is
changed. A successful complete deploy/rollback proof still requires an actual
signed runtime trial of this revised fixture.

## Prepare admission package profile

Actual signed trial `40221931668` at `1381912` failed in guest preparation before
any observer command or native deployment was observed. Its sanitized summary
retained `ValueError`, ordinal zero and no completed trials, with successful VM
and input cleanup. It did not identify the exact rejected source or metadata.
The current source required every fixed system tool to have mode0755. Debian's
[official mount package](
https://deb.debian.org/debian/pool/main/u/util-linux/mount_2.41.5-0+deb13u1_amd64.deb)
contains root:root `usr/bin/mount` with exact mode04755; its package SHA256 is
`eb70a615114ac40123768beb20e302554d5cb7edb33290be7e418ebe1075c878`.
These HTTPS package bytes and archive metadata establish a narrow fixture
profile mismatch, not the failed guest's actual file mode or independent APT
signature verification. The actual trial cause remains unconfirmed.

Only the fixed mount role now requires04755. Other fixed tools still require
exact0755; the unchanged original-file owner retains root ownership, one link,
identity, all mode bits and before/after byte hashes. There is no general setuid
mask, alternate-mode fallback, tool chmod or production policy change. Closed
prepare checkpoints distinguish marker, source, helper, installed binary,
individual fixed tools, socket, each payload/manifest and schema admission.
They expose no raw paths, input names, exception text or configuration. Actual
complete positive and owned-rollback proof remains pending a fresh signed trial;
no clocks, native role caps or deployment behavior changed.


## Recreated rollback selection and report diagnostics

Actual signed trial `40225761365` at `f3559e6` completed its positive transaction.
The negative native transaction returned exit1, `passed: false`, phase
`replace_application` and the closed readiness failure label. The guest then
refused at `negative-report`. Guest and controller cleanup, original-input closes
and QEMU zero were observed. The retained summary omitted rollback booleans and
the specific failed report predicate, so it does not establish whether rollback
failed or which report assertion refused.

A separate source-derived inert regression establishes a fixture obstruction:
after stopping candidate A, the former interposer rejected every application CID
outside the pre-trial baseline. Native rollback can legitimately recreate B with
a new CID. The repaired barrier permits only a read-only pass-through for that
current Compose-selected CID, distinct from stopped A, joined to authenticated B's
image and the exact project, service and run labels. Both dependency originals
must still match their pre-trial ID, image, start, restart and configuration hash.
The private unfinished replacement journal and restored selection contents are
also required. Mutable selection files may have new inodes after native atomic
restoration; exact bytes, private modes and owner checks remain required, while
the original protected configuration directory and untouched input witnesses
remain authoritative. This branch issues no second stop and does not pass an
arbitrary unknown CID. It remains inside the existing20-second service interval
and original guest body. The positive native dependency is unchanged.

All existing strict native report predicates remain required. The failure summary
now includes exact `rollbackAttempted`/`rollbackPassed` booleans or unknown, plus
closed report sub-checkpoints for schema, fields, rollback, timestamps, backup,
evidence path, directory, process and attempt inventory. On a report refusal,
best-effort bounded reads classify existing selection metadata as current,
previous, absent, other or unproven, and the attempt-bound journal as rolled-back,
replace-unfinished, complete, other or unproven. These passive classes expose no
raw IDs, paths, arguments, report text or configuration. Failed or late reads
remain unproven and never replace the original report failure; no Docker query,
new phase or timeout is introduced for these diagnostics.

The old-source regression is retained as a matched failing test. New inert tests

not identify the failed runner's exact rollback outcome or establish a successful
