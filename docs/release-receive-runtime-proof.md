# Signed musl receiver runtime proof

The manual `release-receive-runtime.yml` workflow proves the installed native
`release receive` operation inside one marked, disposable Debian 13 KVM guest on
an ordinary GitHub hosted runner. It has read-only repository and Actions
permissions. It starts no application, service, provider resource or production
host operation, and does not change an installed production caller.

The controller compiles `xtask` and the GNU Ops client before its sole API
credential leaf. Every acquisition and verifier child resolves GH/curl from the
checked private tool directory; only `/usr/bin:/bin` is added for system utilities.
The product client retains its own existing three-tool PATH profile. The keeper owns a fresh
successful `ops-artifact acquire`
invocation for the selected same-head CI run, attempt and signed Ops artifact.
It then retains the complete fifteen-file payload tree and original directory,
invokes the existing retained verifier over those exact originals, and rechecks
every original byte and namespace before execution. This performs six real Ops
verifier calls: three during acquisition and three after retaining the payloads.
The fixture remains subject to the documented same-UID check/read race boundary;
before/after witnesses do not eliminate every transient swap/restore race. A retained JSON
observation alone cannot authorize candidate execution.
The fixed selection JSON is synthesized exclusively from that verified request,
matching the existing runtime transfer semantics. The source-built GNU client measures the signed
musl executable without running
it on the controller. The existing guest transfer, all 33 Ops cases, first install
and exact repeat install run in the same guest. Existing installer behavior still
refuses upgrades or differing installed bytes.

Server authentication is separate: the existing release acquisition checks its
same-head ten-file/four-subject contract. Ops uses its own fifteen-file,
three-subject contract. Both selections must identify the same CI run and attempt.
All eleven original server files, the Ops transfer originals, tools and trusted
fixture sources remain pinned until cleanup. A signed server archive does not
authenticate the Ops executable, and a signed Ops executable does not authenticate
the server release.

Only after installation does a source-bound fixture adapter occupy the guest's
fixed Python receiver entry path. It checks the run marker, root UID and original
installed executable bytes, then directly executes the retained installed musl
binary with `release receive --timeout-seconds 300 --finalization-seconds 30`.
It does not read, proxy or log the stdin frames. The product GNU client's fixed
remote command remains unchanged; no command selector or test flag is added.
This adapter is explicitly part of the proof and is not a production route switch.
The marker-bound preparation installs only Debian curl and CA prerequisites.
The probe records their actual numeric version, OpenSSL/HTTPS admission and
original tool/CA byte pins. The native host's curl/OpenSSL/CA accepted domain
remains the documented receive profile; this proof does not establish generic platform or
malformed-wire parity.

The actual GNU client exercises cached-first and fresh-repeat fetches over real
SSH, with the server URL requested only after receiver Ready. The original positive
guest probe still checks exactly one and two successful attempts respectively.
The two public files must keep identical bytes and device/inode identities on the
repeat. Separate fixed guest assertions prove lock contention and an unfinished
journal refuse before Ready or a new attempt. A deliberately foreign publication
must refuse without replacing that file; the fixture restores only its retained
original. A separate actual download uses a fixed deliberately wrong expected ZIP
hash, requests a new real URL after Ready and requires checksum refusal with the
complete genuine ZIP retained and no selected extraction. This is a full retained
download negative, not a claim of an interrupted or truncated partial transfer.
The final independent probe checks every selected member against original pins,
the exact two-success/two-failure attempt census, unchanged publication and real
lock reacquisition.

One original 1800-second keeper clock includes both authentication acquisitions,
installation and all trials; 120 seconds remain reserved for finalization. Every
child is clipped to its remaining body budget. This deliberately stricter fixture
can refuse a slow otherwise valid standalone acquisition. Native operation N/M
values and production defaults are unchanged. Success additionally requires actual
QEMU exit status zero, authenticated SSH, cloud-init, QMP greeting/capabilities/EOF,
completed drainers, original input checks, known-host retirement, private work
retirement, checked summary output and final handler/umask/deadline settlement.
A receipt line before a later failed close or final status is not proof of success.

The controller admits exact per-phase guest shapes and constructs only closed
public projections. Unknown top-level or nested fields and unexpected negative
statuses refuse; arbitrary guest strings cannot enter the uploaded report.
Only the bounded sanitized `summary.json` is uploaded after terminal success.
Signed targets, tokens, raw streams, SSH keys, disks and private paths remain
private and are not uploaded. A failed proof makes no rollback or production
health claim. The original Python receiver, prepared-helper hash set and product callers
remain unchanged. The CI policy test separately names the new ignored comparison
to keep its dedicated automation caller distinct from the database test route.

This new proof has only inert local tests until a successful same-head signed
artifact run is recorded. No actual VM, network authentication, signed musl
receive execution or operational budget measurement is claimed by its source.
