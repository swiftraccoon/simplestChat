# Fixed maintenance launcher prerequisite runtime proof

This optional manual free-KVM fixture tests the unchanged
[`deploy-public.sh`](../ops/ansible/files/deploy-public.sh) through the authenticated
installed musl Ops binary's `release maintain-prerequisite run` route. It is a
prerequisite experiment for a future complete native maintenance operation.
Installed Python, the operational launcher, host callers and bootstrap stay
unchanged. Source and inert checks alone do not establish the real launcher proof.

The optional workflow invokes the Rust outer controller:

```sh
target/debug/xtask ops-artifact maintain-runtime \
  --run-id "$MAINTAIN_RUN_ID" --run-attempt "$MAINTAIN_RUN_ATTEMPT" \
  --artifact-id "$MAINTAIN_ARTIFACT_ID" --scenario "$MAINTAIN_SCENARIO" \
  --output "$RUNNER_TEMP/maintain-launcher-runtime"
```

The command admits only this exact hosted main workflow and a fresh absolute output
prefix. Run IDs, artifact ID, scenario and output are required. It owns acquisition,
retained inputs, source bundle, QEMU, SSH/QMP, pipe readers, fixed Ansible bootstrap,
the Ready/GO exchange, closed summary and finalization. It does not launch the old
Python outer controller. The guest, Ops33 guest checks, fixed helper modules,
Ansible setup and unchanged operational launcher still execute their existing
Python/shell roles. Every tracked Python source remains byte-identical. This is
an outer-controller migration; it does not claim an entirely Rust guest.

The workflow owns four independent fresh Debian 13 guests: `positive`,
`dirty-source`, `cancel-owned-launcher` and `timeout-stopped-launcher`. Each guest
has its own original 1800-second keeper interval, 120-second finalization reserve,
strict 510-second setup admission and exactly one explicit 1050/60 native call.
Before leaving setup and immediately before invocation it requires 1170 remaining
body seconds. Setup includes actual Ops 6 authentication, retained payload
verification, all 33 install/custody cases, current server 8 authentication plus
current API 2 identity, transfer, cold Docker/images, source import, empty DB and
natural Caddy preparation. The successful Restore fixture's measured setup does
not establish that this larger setup fits 510. Slow or incomplete setup refuses.

The native 925-second known debt is the actual unchanged 900 work cap, three fixed
five-second control phases, five seconds for TERM and five for reap. Native B990
leaves 65 seconds of unmeasured filesystem/scheduling margin. Its run entry captures
one kernel monotonic origin; init receives the same absolute interval, with no
reset at spawn or GO. The outer keeper does not pass its absolute deadline to
native GO. Its independent backstop is the original remaining body and the
invocation's 1050 interval, leaving 120 for observations. No Restore 1200 or full
maintenance 1336 debt is borrowed. These are cooperative bounds, not a guarantee
that blocked kernel I/O or arbitrary scheduling finishes on time.

The 120-second observation phase contains fixed ceilings of 15 for daemon joins,
15 for DB facts, 10 for TLS, 5 for app readiness, 10 for source observations, 15 for
collector retirement, 15 for known CIDs, 15 for the exact network and 10 shared by
both final read-only guard queries. Those 110 seconds leave 10 of unmeasured local
filesystem/scheduling margin. Collector retirement reserves its existing
one-second TERM and five-second reap debt inside its same 15-second end; a late
terminal, close or restored flag refuses success.
After the final live body fence, only local capture/process retirement and
retained-original closes use the original 120-second finalization reserve. No
Docker or firewall query is deferred into that reserve.

Only the signed same-head Ops/server selections from the exact successful CI run
and attempt are accepted. The source-built GNU controller performs fresh/cached
verification and passive ELF inspection; actual guest execution uses the installed
authenticated musl inode.
The Ops 33 process is separate: installed content and namespace are freshly joined
after it returns, then that exact read-only installed FD spans native execution
and finalizers. Earlier JSON is passive and supplies no execution authority.

A local source bundle carries the selected commit's original objects. The guest
creates one explicit shallow boundary, imports that bundle, checks detached HEAD,
its tree, connectivity, one-commit reachability and clean worktree before use.
This proves the selected shallow tree; it does not claim complete Git history.
No remote Git fetch occurs in the guest. Original launcher/helper/template and 36
migration bytes are retained. The dirty case changes only the fixed nonexecuted
README after that clean-tree check; execution helpers remain byte-identical.

The fixture renders original templates with coordinated synthetic secrets and the
dotted private origin `maintain.localhost`. The exact source Caddyfile, normal
UID10001 restrictions and operational split-path mounts remain intact. Only
fixture nonce labels, loopback exposure and the explicitly owned internal bridge
are added. PostgreSQL starts with empty application schema and the actual role/
HBA/password profile; setup does not migrate or seed ahead of the launcher. The
positive launcher itself performs migrations, grants, owner/lobby seed, runtime
policy, initial backup and public proxy start. Backup evidence covers the actual
custom-dump header, digest and retained bytes; it is not a separate restore test.

Natural seven-file CA/leaf materials are generated by the fixed Caddy image.
Independent public SSL APIs verify SNI, hostname, leaf/chain and dates against the
retained public root in a private context. The actual launcher-created fresh proxy
must reuse those same seven originals. No manual fixture certificate, TLS rewrite,
public CA request or host-global trust change is used. Its metrics 404 TLS probe is
separate from the actual backend readiness and synthetic DB checks. The earlier
exact-source Caddy experiment establishes its own TLS-only profile, not this
whole launcher transaction.

An exhaustive guest nftables guard and physical capture cover external contact,
including Docker's embedded DNS forwarding. Images/packages are acquired before
the guard is installed. The guard stays installed through guest exit and retires
through the exact owned VM's teardown; successful nftables deletion is not
claimed. Capture evidence covers its actual observed interval. No public host,
chat data, paid capacity or production transaction is involved.

A live bounded daemon event collector is started during setup and joined to an
actual known marker before native admission. Expected actor/exec and current
inventory joins remain distinct from native PID-namespace facts. Docker's event
pubsub can drop records; a marker, EOF or 256-entry historical ring is not a global
gap-free history proof. Missing expected joins, unknown creates or unexpected
observed effects make the case unproven. They never authorize cleanup by name.
Only complete known fixture CIDs and the exact empty owned network may retire.
The existing process pump proves direct-child status and pipe completion;
independent retirement of every guest client group is not inferred after reap.
The PG catalog requires exact fixed launcher/health exec commands and per-ID
create/start/die/status joins. Missing boundary-spanning health completions or
different engine event schemas refuse this finite profile. Known Moby source
bindings describe the reviewed schema; exact pinned-engine delivery remains an
actual-runtime requirement, rather than a source-only claim.

The dirty-source case requires actual launcher start/nonzero status, exact
README-only dirtiness, stable complete input hashes, independently successful
same compose/image/source preconditions, configuration outcome and no observed
unexpected mutations plus fresh inventory/DB/source witnesses. This is a
source-bound refusal join, not a directly traced Bash/Git failure site. Cancel
requires actual nested readonly first-Compose-ps identity and kernel STOP proof,
then a real SIGTERM self-raised on native Run. It proves that controlled
cancellation profile, not an external operator signal. Timeout requires the same
readonly stopped-client proof and the real unchanged 900 elapsed work cap. Missed
or changed client observation is unproven; no faster timeout substitutes for it.

All dumps, keys, raw streams, resolved config, event records and private evidence
stay inside the disposable prefix/guest. The always-retained artifact is only the
closed source/status/checkpoint/boolean summary. Null incomplete hashes and actual
signed statuses remain null or actual; counters are not clamped to manufacture a
positive. Expected native1/143/124 are separate from the guest experiment's final
verdict. Success also requires all known finalizers, actual SSH/QEMU0, handler and
umask restoration, stdout and the original final signal/deadline fence.
The retained first I/O, policy or explicit clock/signal refusal remains its own
failure category when a later cleanup deadline also determines the final status.
