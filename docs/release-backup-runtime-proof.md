# Signed musl standalone backup-verification runtime proof

This optional manual free-KVM fixture exercises the complete public
`release backup verify` route in the authenticated installed Ops binary. The
three fixed cases each own an independent fresh Debian13 guest and exactly one
native invocation. Existing installed Python, nightly/offsite callers and
operational bootstrap remain unchanged. No application, Caddy or server artifact
is required or authenticated by this fixture.

The controller owns current Ops acquisition and retained verification (six actual
GH attestation verifier invocations), the exact original fifteen-member payload,
transfer, install/repeat and all33 existing Ops custody/install cases. It retains
the same installed musl inode around the public CLI. A source-built GNU binary is
used only for passive ELF inspection on the controller, never as authenticated
musl execution evidence. The33-case keeper is a separate SSH process; content and
selection are joined across that handoff. The retained installed FD begins after
Ops33 and spans the public restore CLI and its finalizers. Saved JSON is passive
and cannot replace authentication.

Run only the dedicated workflow on main with exact signed same-head Ops run,
attempt and artifact pins after the complete Restore feature has passed CI and
been signed. The workflow's fixed matrix is `current`,
`historical-subset-failed-release`, and `privacy-invalid`. A missing or failed case
cannot be called a complete three-case proof. There is no host/image/command
selector and no new always-required CI gate.

Each keeper starts its original1800-second clock before effects, keeps120 seconds
for finalizers and bounds all setup/auth/install/cold engine/image/seed work to
360 seconds. It checks that live setup phase and at least1320 seconds of remaining
body before widening; the guest Ready/GO protocol repeats that admission. The
public command is always explicit1200/120, with no default or increase to the
native maximum1800. The remaining120 body seconds are independent observation
and fixture PostgreSQL cleanup allowance; slow roles may still refuse. The
existing QEMU1800 limit is unchanged.

Cold setup has not been measured. If it cannot meet360, the proof remains
unproven; another helper's clock or service budget cannot be borrowed. Native
role-debt arithmetic is785 inside B1080, leaving295 for filesystem/scheduling
work. This is not a capacity or blocked-kernel hard-wall guarantee. Native R160
stays inside B; strict readiness remains one live30 phase including settlement.

The root-owned fixture uses the repository-pinned PG18 image, all36 original
migration files/SHA384 values, exact operational schema, runtime grants and fixed
`restore-verify.sql` root0644. It creates only a network-none source PostgreSQL
at the fixed image-identity anchor. The source ledger and synthetic aggregates
are queried before and after native execution. The closed
`sourceLedgerAndCountsUnchanged` fact covers those observations, alongside the
same original anchor CID/image; it does not claim every database row or grant was
rehashed. Backup/source bytes must remain unchanged. Dumps contain synthetic data, stay
private/root0600 and are capped at1MiB in this fixture, below the product64MiB
limit. The manifest is a locally generated strict seven-field fixture record,
not a signed server artifact or proof of a production backup.

The current case restores the current schema and six exact aggregates, then
runs amcheck and requires native cleanup, outcome and freshness. The historical
case uses the real pre022 ledger as a nonempty subset of all packaged migrations,
with `passed=false` and no backup receipt. The privacy case restores a valid
archive/ledger carrying a deliberate app grant on the private operations schema;
it must reach actual fixed SQL refusal, remove its disposable DB and retain the
previous passive freshness bytes. It cannot pass via a digest/admission shortcut.

A read-only observer inspects only the generated native actor's exact
name/label/image/CID join. A missed short-lived inspection window is unproven,
never reconstructed from source or a synthetic response. Bounded passive
initial/created/final restore-record hints select only one actual inspect sample;
their atomic generation changes supply no cleanup or authentication authority.
The real daemon history must join ordered readiness/role/restore/ledger/verify/
amcheck events and actual actor destruction, alongside the retained native
ledger output and final absence checks. Every exec must join a unique `execID`
across create/start/die, the exact fixed command and an actual bounded exit code.
A start event alone precedes task execution and cannot prove completion. The
conservative event profile is source-bound to
[Moby v28.2.2 exec emission](https://github.com/moby/moby/blob/v28.2.2/daemon/exec.go)
and [completion](https://github.com/moby/moby/blob/v28.2.2/daemon/monitor.go).
The repository's pinned Docker29.8.2 event schema remains unproven until the
actual guest run; missing or different evidence refuses the proof. Final selectors and
exact-CID absence are independent from native report claims. Fixture cleanup
removes only its separately joined source CID; it never removes native leftovers
by name to hide a failure. Known fixture daemon cleanup stays inside the original
guest body, even
on a negative path; final reserve is for local owners and VM teardown. Whole
QEMU teardown contains remaining guest resources. The first failure category
survives a later cleanup signal/deadline, which is recorded separately from the
actual native status and the ultimate guest/keeper exit.

The existing process pump proves direct child status/pipe completion. It does not
independently prove every guest client group retired after a consuming reap;
there is no post-reap signalling. The native binary owns its internal role
lifecycle; its readonly-input, SDK clone-close exception, fsync and lock-through-
output properties retain their source/inert-test qualifications. Post-run
acquisition of the same workload-lock inode proves only its observed release.

All dumps, SQL, raw streams/config and DB rows remain private. The always-retained
summary has a closed source/artifact/case/checkpoint/status/boolean projection;
unknown nested fields or arbitrary failure text cannot escape. A positive
requires actual signed QEMU0 and all controller input/session/finalizer facts,
then the original handler/umask/output/signal/deadline fence. Earlier success text
or a passive freshness file cannot override a final nonzero status.

Source, inert tests and workflow/Ansible checks pass for this integrated fixture.
Actual authentication/installed CLI/PostgreSQL/amcheck/KVM execution remains
unrun. This fixture does not establish same-selector repeat,64MiB capacity,
unknown-create delivery recovery, arbitrary injected native close/timeout faults,
production restore, app availability, offsite recovery or caller cutover.
